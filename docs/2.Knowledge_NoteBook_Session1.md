# 📓 Ghi chú Kiến thức - Phiên 1: Khởi tạo PostgreSQL qua WSL

Tài liệu này tổng hợp lại toàn bộ các câu lệnh và khái niệm quan trọng bạn đã thực hành trong phiên làm việc đầu tiên của dự án Mini SMA. Việc ghi chép lại sẽ giúp bạn có một cuốn "từ điển" cá nhân để tra cứu cực kỳ nhanh chóng sau này.

---

## 1. Các khái niệm cốt lõi (Core Concepts)

*   **WSL (Windows Subsystem for Linux):** Là một tính năng của Windows cho phép bạn chạy một môi trường Linux (như Ubuntu) trực tiếp trên Windows mà không cần cài máy ảo (Virtual Machine) nặng nề hay cài song song (Dual Boot).
*   **Môi trường độc lập:** Khi dùng WSL, ổ cứng của Windows (PowerShell) và Linux (Bash) là riêng biệt. Các câu lệnh Linux như `sudo` hay `apt` sẽ **bị báo lỗi** nếu bạn gõ ở bên ngoài Windows PowerShell.
*   **Package Manager (Trình quản lý gói - `apt`):** Giống như App Store của điện thoại. Nó giúp bạn tải, cài đặt và cập nhật phần mềm trên Ubuntu một cách tự động thông qua câu lệnh.
*   **Superuser `postgres`:** Khi PostgreSQL được cài đặt xong, nó tự động tạo ra một tài khoản quản trị viên tối cao mang tên `postgres`. Bạn bắt buộc phải đóng vai tài khoản này mới có thể cấu hình Database ở những bước đầu tiên.

## 2. Từ điển Câu lệnh (Command Glossary)

### Thao tác với WSL (Trên Windows PowerShell)

| Câu lệnh | Ý nghĩa | Lời khuyên thực tế |
| :--- | :--- | :--- |
| `wsl --install` | Yêu cầu Windows tự động tải và cài đặt bản phân phối Linux mặc định (thường là Ubuntu). | Chỉ cần chạy 1 lần duy nhất khi cấu hình máy mới. |
| `wsl -l -v` | Xem danh sách các máy ảo Linux đang có trên máy và trạng thái của chúng (Đang chạy hay đã tắt). | Dùng để kiểm tra xem mình có đang bị nhầm môi trường không (Ví dụ: nhầm sang docker-desktop). |
| `wsl -d Ubuntu` | Chỉ định đích danh (`-d` là distribution) khởi chạy môi trường Ubuntu. | Dùng câu lệnh này để "chui" vào Linux một cách an toàn và chính xác nhất. |

### Thao tác bên trong Linux (Trên Ubuntu Terminal)

| Câu lệnh | Ý nghĩa | Lưu ý |
| :--- | :--- | :--- |
| `sudo apt update` | Cập nhật "danh bạ" các phần mềm mới nhất từ máy chủ của Ubuntu. | **Luôn luôn chạy lệnh này** trước khi cài đặt bất cứ phần mềm mới nào. |
| `sudo apt install postgresql postgresql-contrib -y` | Cài đặt hệ quản trị PostgreSQL và các công cụ mở rộng (contrib). | Cờ `-y` giúp hệ thống tự động đồng ý cài đặt mà không cần dừng lại hỏi bạn. |
| `sudo service postgresql start` | Đánh thức / Khởi động dịch vụ Database chạy ngầm. | Nếu thay `start` bằng `status`, bạn sẽ xem được Database đang chạy hay tắt. |
| `sudo su - postgres` | Lệnh Switch User: Giúp bạn "hóa thân" thành tài khoản siêu quản trị viên. | Dấu nhắc lệnh sẽ chuyển từ màu xanh `...$` sang dạng `postgres@...`. |

### Thao tác cấu hình Database (Trong môi trường `psql`)

*   `psql`: Lệnh dùng để mở giao diện gõ mã SQL của PostgreSQL.
*   `ALTER USER postgres WITH PASSWORD '123456';`: Câu lệnh SQL dùng để đổi mật khẩu cho user postgres thành `123456`. (Lưu ý luôn phải có dấu chấm phẩy `;` ở cuối).

## 3. Nhật ký Gỡ lỗi (Debugging Log)

Trong quá trình kết nối Database qua DBeaver, chúng ta đã bắt gặp và giải quyết 2 "cái bẫy" kinh điển:

### Lỗi 1: Xung đột cổng mạng (Port Conflict)
*   **Hiện tượng:** DBeaver báo lỗi sai mật khẩu (`FATAL: password authentication failed`) dù nhập đúng `123456`.
*   **Nguyên nhân:** Máy tính Windows đang có sẵn một phần mềm PostgreSQL (bản `.exe`) chạy ngầm và chiếm cổng `5432`. Do đó, DBeaver trên Windows đã kết nối nhầm vào Database cũ này thay vì kết nối vào máy chủ Linux (WSL).
*   **Bài học:** Luôn gỡ bỏ hoặc tắt (Stop Service) các môi trường Database cũ trên Windows để tránh tranh chấp cổng giao tiếp (Port) với Linux/Docker.

### Lỗi 2: PostgreSQL từ chối kết nối bên ngoài (Connection refused)
*   **Hiện tượng:** DBeaver báo lỗi `Connection refused` dù dịch vụ trong Linux đã được `start`.
*   **Nguyên nhân:** Mặc định, PostgreSQL cài trên Linux chỉ cho phép các ứng dụng bên trong nội bộ Linux kết nối (thông qua địa chỉ `localhost` của Linux). Nó từ chối mọi yêu cầu từ bên ngoài (Windows).
*   **Cách giải quyết (Chỉnh sửa cấu hình bảo mật):**
    1. Dùng lệnh `sudo nano /etc/postgresql/18/main/postgresql.conf` để mở file cấu hình bằng trình soạn thảo `nano`.
    2. Tìm dòng `#listen_addresses = 'localhost'`, bỏ dấu `#` và đổi `localhost` thành `*` (nghĩa là cho phép mọi địa chỉ kết nối vào).
    3. Lưu lại bằng **Ctrl + O** (Enter) và thoát bằng **Ctrl + X**.
    4. Khởi động lại dịch vụ bằng lệnh: `sudo service postgresql restart`.

---

**💡 Mẹo nhỏ của BA:** Hãy thường xuyên xem lại file này. Trong tương lai, khi triển khai Docker hoặc đẩy code lên Server thật (Production), những câu lệnh Linux cơ bản này sẽ là công cụ cứu cánh giúp bạn bắt "bug" và cấu hình hệ thống cực kỳ hiệu quả!

## 4. JavaScript vs TypeScript

### Điểm khác biệt cốt lõi

| | **JavaScript (JS)** | **TypeScript (TS)** |
| :--- | :--- | :--- |
| **Kiểu dữ liệu** | Dynamic Typing — tự do, không khai báo kiểu | Static Typing — bắt buộc khai báo kiểu (`number`, `string`,...) |
| **Phát hiện lỗi** | Lúc **runtime** (khi code đang chạy) | Lúc **compile-time** (khi viết code, IDE báo ngay) |
| **Chạy trên Node.js** | ✅ Trực tiếp | ❌ Cần compile sang JS trước |
| **Phù hợp khi** | Dự án nhỏ, học tập, prototype | Dự án lớn, team đông, cần an toàn kiểu dữ liệu |

### Quy trình chạy TypeScript

```
file.ts  →  [tsc compiler]  →  file.js  →  [Node.js Runtime]  →  Chạy!
```

> **`ts-node`** là công cụ gộp 2 bước trên lại thành 1 lệnh, tiện trong development — nhưng bước compile **vẫn diễn ra bên trong**, không phải biến mất.

### Quyết định cho dự án Mini SMA
- **Backend (Node.js):** Giữ **JavaScript** → tập trung vào logic, ORM, API
- **Frontend (React):** Dùng **TypeScript** → học TS đúng ngữ cảnh (props, state typing)

## 5. Hệ thống Module của Node.js (CommonJS vs ES Module)

Node.js có **2 hệ thống module** khác nhau — đây là nguồn gốc của một lỗi rất phổ biến:

| | **CommonJS (CJS)** | **ES Module (ESM)** |
| :--- | :--- | :--- |
| **Cú pháp nạp** | `const x = require('y')` | `import x from 'y'` |
| **Cú pháp xuất** | `module.exports = x` | `export default x` |
| **Khai báo trong** `package.json` | `"type": "commonjs"` (mặc định) | `"type": "module"` |
| **Xu hướng** | Legacy, vẫn rất phổ biến trong Node.js | Hiện đại, chuẩn của trình duyệt và tương lai |

> ⚠️ **Quy tắc vàng:** `package.json` khai báo kiểu nào → code **phải** dùng cú pháp tương ứng. Dùng lẫn lộn sẽ gặp lỗi ngay.

### 🐛 Bug đã gặp & cách fix

```
SyntaxError: Cannot use import statement outside a module
```

- **Nguyên nhân:** Dùng cú pháp `import` (ESM) nhưng `package.json` khai báo `"type": "commonjs"`.
- **Fix:** Đổi sang cú pháp CommonJS:
  ```js
  // ❌ Sai (ESM syntax)
  import express from 'express';

  // ✅ Đúng (CommonJS syntax)
  const express = require('express');
  ```

## 6. Cấu trúc file `src/server.js` — Entry Point của Backend

```js
const express = require('express');   // 1. Nạp framework Express

const app = express();                // 2. Khởi tạo ứng dụng

app.get('/', (req, res) => {          // 3. Định nghĩa route mẫu
    res.send('Hello World!');
});

app.listen(3000, () => {              // 4. Lắng nghe trên port 3000
    console.log('Server is running on port 3000');
});
```

**Giải thích luồng:**
1. `require('express')` → Trả về một **function** (không phải object)
2. Gọi function đó `express()` → Trả về object `app` chứa toàn bộ API của Express
3. `app.get(path, handler)` → Đăng ký route xử lý HTTP GET request
4. `app.listen(port, callback)` → Mở cổng lắng nghe, gọi callback khi sẵn sàng

## 7. Quản lý gói (Package Management) trong Node.js

Khi cài đặt thư viện bằng NPM (Node Package Manager), các thư viện được chia làm 2 loại trong file `package.json`:

| | **`dependencies`** | **`devDependencies`** |
| :--- | :--- | :--- |
| **Mục đích** | Các thư viện cần thiết để ứng dụng **chạy** trong môi trường thực tế (Production). | Các công cụ hỗ trợ lập trình viên trong quá trình **phát triển** và **test** (Development). |

| **Môi trường Prod**| Sẽ được cài đặt khi chạy `npm install --production`. | Bị **bỏ qua**, giúp tiết kiệm dung lượng ổ cứng cho server Production. |

## 8. Cấu trúc mạng (Networking) của WSL2

*   **Bản chất của WSL2:** Là một máy ảo Linux (chạy hạt nhân Linux thật) nằm bên trong Windows. Do đó, WSL2 có địa chỉ IP riêng, tách biệt với Windows.
*   **Vấn đề IP Động:** Mỗi khi khởi động lại máy tính, WSL2 sẽ cấp phát một IP mới ngẫu nhiên (ví dụ `172.17.x.x`). Điều này gây khó khăn khi ứng dụng Node.js (chạy trên Windows) muốn kết nối cố định vào PostgreSQL (chạy trên WSL2).
*   **Giải pháp - Mirrored Networking (`localhost`):** Trên các phiên bản Windows 11/WSL2 mới, Microsoft hỗ trợ tự động định tuyến. Khi ta kết nối vào `localhost:5432` trên Windows, mạng sẽ tự động "xuyên không" trỏ thẳng vào cổng `5432` của máy ảo Linux. Do đó, luôn ưu tiên sử dụng `localhost` thay vì IP tĩnh hoặc lấy IP động.

## 9. Prisma ORM: Công cụ giao tiếp với Database

**ORM (Object-Relational Mapper)** là một công cụ giúp lập trình viên viết code JavaScript/TypeScript (hướng đối tượng) để thao tác với Database thay vì viết câu lệnh SQL thuần túy.

*   **`prisma` (CLI):** Cài bằng `--save-dev`. Là công cụ dòng lệnh dùng để đồng bộ Database, khởi tạo file cấu hình (`npx prisma init`) và đọc cấu trúc DB (`npx prisma db pull`).
*   **`@prisma/client`:** Là thư viện thực tế được nhúng vào code Node.js để thực hiện các thao tác (Thêm, Sửa, Xóa, Tìm kiếm) trong lúc ứng dụng đang chạy.
*   **`.env`:** File bí mật chứa chuỗi kết nối (Connection String) `DATABASE_URL`. Tuyệt đối không bao giờ được đưa file này lên Github (phải đưa vào `.gitignore`).
*   **Chuỗi kết nối (Connection String):** `postgresql://[USER]:[PASSWORD]@[HOST]:[PORT]/[DATABASE_NAME]`
*   **Cảnh báo khi `db pull`:** Việc Prisma báo vàng `check constraints` là bình thường và an toàn. PostgreSQL của bạn vẫn kiểm tra các ràng buộc đó khi có dữ liệu mới được lưu vào, Prisma chỉ đang báo rằng nó không thể hỗ trợ mô phỏng lại các ràng buộc đó trong code JavaScript.

## 10. Kiến trúc Phân tầng (Layered Architecture) trong Backend

Khi viết API, chúng ta không nhồi nhét tất cả code vào một file `server.js` duy nhất mà chia thành 3 tầng riêng biệt. Việc này giống như tổ chức một nhà hàng:
1.  **Route (Cửa ra vào/Lễ tân):** Chuyên tiếp nhận yêu cầu (Request) từ người dùng dựa trên URL (ví dụ: `GET /api/products`). Nó không trực tiếp lấy dữ liệu mà chỉ định đường cho Controller xử lý.
2.  **Controller (Người Điều phối/Phục vụ):** Nhận order từ Route, hiểu người dùng muốn gì, sau đó sai bảo Service đi lấy/xử lý dữ liệu. Sau khi có kết quả, Controller chịu trách nhiệm đóng gói (format) thành file JSON và trả về (Response) cho người dùng.
3.  **Service (Bếp trưởng/Thủ kho):** Nơi chứa toàn bộ logic nghiệp vụ cốt lõi. Đây là tầng duy nhất được phép giao tiếp với Database (thông qua Prisma) để kéo, sửa, hoặc xóa dữ liệu.

*Nguyên tắc:* Luồng dữ liệu chỉ đi một chiều: **Route -> Controller -> Service -> Database**.

## 11. Biến Môi Trường (Environment Variables) & Lỗi Bất Đồng Bộ

*   **Tại sao không Hardcode?** Tuyệt đối không viết thẳng (hardcode) chuỗi kết nối chứa mật khẩu (ví dụ: `postgresql://postgres:123456...`) vào trong mã nguồn (file `.js`). Làm vậy sẽ gây lộ lọt bảo mật khi đưa lên GitHub, và cực kỳ khó khăn khi chuyển đổi code giữa máy cá nhân và máy chủ thật.
*   **Giải pháp:** Đặt chuỗi kết nối vào file `.env`. Git sẽ bỏ qua file này.
*   **Thư viện `dotenv`:** Trong Node.js, để đọc được file `.env` và đưa vào biến toàn cục `process.env`, ta phải gọi lệnh `require('dotenv').config()`.
*   **Lỗi kinh điển về thứ tự (Order of Execution):** Do Node.js chạy từ trên xuống dưới, lệnh `require('dotenv').config()` BẮT BUỘC phải nằm trên cùng của file `server.js`. Nếu nạp các file khác (như `productRoutes` -> `db.js`) trước khi nạp `dotenv`, hệ thống sẽ gọi `process.env.DATABASE_URL` khi nó vẫn còn trống (undefined), dẫn đến lỗi xác thực Database (`client password must be a string`).

## 12. Prisma Client (Sinh code tự động) & Driver Adapter

*   **`npx prisma generate`:** Lệnh này đọc cấu trúc bảng từ file `schema.prisma` và tự động sinh ra một bộ code (Object) để Node.js có thể gọi các hàm như `.findMany()`, `.create()`.
*   **Đường dẫn tương đối (Relative Path):** Khi import (require) code nội bộ, bắt buộc phải dùng đường dẫn tương đối như `./` (thư mục hiện tại) hoặc `../` (lùi ra thư mục cha). Nếu viết `require('prisma')`, Node.js sẽ nhầm tưởng bạn đang gọi thư viện bên thứ 3 từ `node_modules`.
*   **Driver Adapter (Trong Prisma bản mới):** Ở các phiên bản Prisma gần đây (v6, v7), cơ chế kết nối mặc định yêu cầu phải có "cầu nối" (Adapter) để giao tiếp với DB. Do đó, ta phải cài thêm `pg` và `@prisma/adapter-pg`, sau đó bọc (wrap) connection pool của Postgres vào trong Prisma Client để hệ thống hoạt động ổn định nhất.

## 13. Express Middleware Pipeline (Luồng xử lý từ trên xuống dưới)

*   **Bản chất:** Express xử lý các Request đi qua một "đường ống" (pipeline) chứa các middleware theo **đúng thứ tự khai báo từ trên xuống dưới** trong file `server.js`.
*   **Lỗi kinh điển (`req.body` trả về rỗng/undefined):** Xảy ra khi bạn khai báo các Route (`app.use('/api/...', routes)`) nằm bên trên dòng cấu hình đọc JSON (`app.use(express.json())`).
*   **Cách giải quyết:** Khi request đi qua route trước, nó chưa được "dịch" sang JSON nên Controller không hiểu được. Do đó, các cấu hình parse body như `express.json()` hay `express.urlencoded()` luôn luôn phải được đặt ở phía trên cùng, trước khi định nghĩa bất kỳ Route nào cần đọc dữ liệu từ Client gửi lên.

## 14. Testing API vs Seed Data

Trong quá trình phát triển Backend, chúng ta cần phân biệt rõ hai phương pháp chuẩn bị/kiểm tra dữ liệu:

1.  **Seed Data (Dữ liệu mẫu ban đầu):** Là việc dùng script (như `prisma db seed` hoặc gõ SQL) bơm thẳng dữ liệu giả trực tiếp vào Database. Việc này giúp Database nhanh chóng có dữ liệu để phục vụ cho việc xây dựng Frontend hoặc test các API `GET` (đọc dữ liệu danh sách).
2.  **Testing API POST (Kiểm thử luồng đi của hệ thống):** Khi viết một API `POST` (Tạo mới), mục đích của chúng ta không chỉ là "có dữ liệu trong DB", mà là **kiểm tra sự toàn vẹn của cả hệ thống Backend**:
    *   Route có bắt đúng đường dẫn URL không?
    *   Controller có parse được file JSON do người dùng gửi không?
    *   Service có nhận đủ tham số và gọi đúng hàm Prisma không?
    *   **Kết luận:** Để test API POST, bắt buộc phải dùng các công cụ giả lập Frontend (như **Postman**, **cURL**, **Thunder Client**) để bắn một HTTP Request. Nó giúp dữ liệu đi xuyên qua toàn bộ các tầng (Layer) của hệ thống. Tuyệt đối không dùng phương pháp bơm Seed Data để thay thế cho bước kiểm thử này.
